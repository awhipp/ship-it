Phase 01 gh issue list --label "ship-it:map"

Explore Technical Trade-offs Upfront

When a feature has multiple viable paths, map out architectural questions through structured conversation before touching code.

What this step does

Surfaces architectural decisions early. The assistant presents technical alternatives with trade-offs so choices like state management, schemas, or protocols are decided deliberately.

Inputs & Outputs

Inputs: Feature goals, codebase constraints, and open technical trade-offs
Outputs: A decision map issue documenting settled choices and outstanding questions

Where you step in

Technical direction: You review the trade-offs between patterns or tools and select the direction that matches your architecture.

Keeping on track

Preventing Drift: Stops the assistant from quietly making assumptions that would be costly to undo later. Foundational decisions are settled before any code is generated.

Phase 02 gh issue list --label "ship-it:spec"

Establish the Behavioral Contract

Define unambiguous user stories, acceptance criteria, and explicit boundaries before implementation begins.

What this step does

Translates broad goals into concrete, verifiable requirements. Documents user stories, designated test seams, and intentionally excluded features to prevent scope creep.

Inputs & Outputs

Inputs: Feature goals, settled architecture choices, and repository conventions
Outputs: A validated specification issue with verifiable user stories and an out-of-scope checklist

Where you step in

Boundary sign-off: You confirm acceptance criteria reflect true user needs and verify the out-of-scope boundaries to keep the project focused.

Keeping on track

Preventing Drift: A fresh-eyes review pass in an isolated context audits the specification for ambiguities, untested assumptions, or vague requirements before work begins.

Phase 03 gh issue list --label "ship-it:ticket"

Deconstruct into Sequential Units of Work

Break the specification into self-contained tasks with explicit dependency order so progress is steady and predictable.

What this step does

Divides the feature into an ordered tasklist where each issue encapsulates one working increment with clear prerequisites and isolated acceptance tests.

Inputs & Outputs

Inputs: The validated feature specification and its identified test seams
Outputs: A sequence of GitHub issues linked with markdown dependency checklists

Where you step in

Task sequencing: You verify that each ticket represents a manageable unit of work with clear deliverables that can be reviewed independently.

Keeping on track

Preventing Drift: Work only proceeds on tickets whose prerequisites have already been merged and verified, eliminating broken dependencies and chaotic branch merges.

Phase 04 gh issue edit <num> --add-assignee "@me"

Build with Test-First Discipline

Tackle one ticket at a time in a focused session, using Red-Green test cycles to prove each requirement works.

What this step does

Applies test-driven development to build the feature. The assistant creates an automated test reproducing the ticket criteria, confirms it fails, and then writes the minimal code to pass.

Inputs & Outputs

Inputs: The unblocked ticket, its acceptance criteria, and the working branch
Outputs: A recorded test failure log, passing test suite, and minimal code diff

Where you step in

Course correction: If implementation exposes an edge case or an unpredicted technical obstacle, the assistant pauses and asks you for guidance instead of inventing an undocumented workaround.

Keeping on track

Preventing Drift: Demonstrating test failure before implementation ensures the test is genuinely validating the required behavior and prevents false passes.

Phase 05 gh issue view <num> --comments

Audit the Diff from Two Perspectives

Perform an independent review that evaluates code craft and functional correctness separately.

What this step does

Evaluates branch changes on two independent axes: codebase standards (modularity, readability, conventions) and specification fidelity (ensuring all user stories pass without unintended changes).

Inputs & Outputs

Inputs: The branch diff, team conventions, and ticket acceptance criteria
Outputs: A two-axis review scorecard with clear findings and a merge recommendation

Where you step in

Final merge sign-off: You inspect the findings from both review axes and make the final call to merge the pull request into your branch.

Keeping on track

Preventing Drift: Evaluating code structure and behavior separately ensures clean aesthetics don't mask missing logic, and working code doesn't excuse sloppy patterns.

Architectural Pillars & Principles

Built from first principles to keep autonomous agents bounded, truthful, and rigorously verified. Four architectural guarantees that eliminate chaotic agent drift.

Pillar 01

Context Hygiene

Clearing context as a core feature

Monolithic chats suffer from token bloat and severe reasoning degradation. ship-it treats context clearing as a fundamental engineering primitive: every phase and ticket slice starts in a clean, fresh session anchored to the git merge-base, ensuring zero context rot and sustained model precision.

Zero Context Rot Fresh Session per Ticket Git Merge-Base Anchor
Pillar 02

Adversarial Validation Gate

Fresh-session pre-build auditing

When the same model session authors a spec and approves it, author confirmation bias masks hidden flaws. ship-it enforces a 2-Tier Context Isolation Protocol: an independent auditor evaluates specs, maps, and ticket DAGs in a fresh session before any implementation code is written.

2-Tier Context Isolation Zero Confirmation Bias Pre-Build Audit
Pillar 03

Two-Axis Code Review

Coding Standards vs. Spec Fidelity

Review verdicts must never collapse into a single subjective rubber-stamp. ship-it audits diffs along two orthogonal axes: Axis 1 inspects Fowler refactoring heuristics and architectural hygiene, while Axis 2 systematically validates line-by-line ticket acceptance criteria.

Axis 1: Fowler Standards Axis 2: Spec Fidelity Dual-Verdict Gate
Pillar 04

GitHub-Native Traceability

Issues as a transparent state machine

No proprietary SaaS, no external telemetry dashboards, and zero vendor lock-in. ship-it models the full SDLC directly inside GitHub: issues act as the state machine, tasklists form dependency DAGs, and standard git branches and pull requests house the verified audit trail.

Issues as State Machine Zero Proprietary SaaS 100% Git-Native
